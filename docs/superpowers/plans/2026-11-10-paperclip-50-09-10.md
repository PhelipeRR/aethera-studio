# Paperclip 50.09/50.10 Implementation Plan

> **For agentic workers:** This plan is gated: the audit and decision must be approved before any Paperclip runtime code is written.

**Goal:** Establish whether Paperclip belongs beside the Singularity Core without duplicate task execution, then implement only the approved boundary.

**Current decision state:** The user approved **option A** and authorized the broader implementation. PoC 50.09 is complete; the isolated 50.10 adapter is implemented without automatic activation.

**Architecture:** The Singularity Core remains the sole executor. Paperclip, if accepted, is an external control-plane adapter using `external_ref`, idempotency and lease state; it never starts a local TaskEngine or agent process directly. If the comparison finds no safe value, record the non-integration decision and ship no Paperclip dependency.

**Tech Stack:** Existing `packages/core`, `packages/shared/src/core-api`, TaskEngine lease/idempotency, isolated test doubles, and a disposable Paperclip PoC environment only after approval.

**Spec:** `docs/plans/singularity-master-plan.md` §6; `docs/architecture/adr-core-01-singularity-core.md` §6.

## Global Constraints

- No Paperclip package or runtime integration is added to NeuralBridge by 50.09. The Paperclip process used for the PoC was disposable, loopback-only and outside the product runtime.
- The Core is the only executor; every external request must carry an idempotency key and stable `external_ref`.
- Preserve NeuralBridge identifiers, existing TaskEngine behavior, memory/RAG, agents, MCP and Companion.
- Do not expose the Core publicly; remote access remains private and authenticated through the existing boundary.
- No commit or push is part of this plan unless separately authorized.

## Review Focus

- Duplicate execution after retries or restarts — prove one lease owner and one resulting task.
- Paperclip retry/timeout semantics — prove idempotent reconciliation rather than a second run.
- Authentication and secret handling — prove no Paperclip token reaches the renderer or logs.
- Capability mismatch — prove unsupported Paperclip features fail closed instead of bypassing Core policy.
- Rejection path — prove the application remains fully functional with Paperclip absent or disabled.

## PoC evidence and limitations

- Real Paperclip API checks: health, company creation, issue creation, issue read and cancellation all succeeded on
  the isolated loopback server.
- The first official dev runner path was blocked by an upstream `grok commandDigest` attestation mismatch. The PoC did
  not regenerate or weaken that attestation; direct server startup was used after building only missing local TypeScript
  artifacts (`shared` and `plugin-sdk`).
- No agent was onboarded and no model/provider was called. Therefore execution latency, provider cost, and Paperclip
  heartbeat behavior with a live agent remain unmeasured and are explicit 50.10 risks.
- The server emitted a Node `MaxListenersExceededWarning` during plugin lifecycle startup and reported no database
  backup yet. Both are limitations of the disposable local run, not fixes to apply in NeuralBridge.
- The isolated state is disposable and must not be reused as a production database.
